# 严格仲裁协议

Strict Arbitration 的目标是让项目制作与独立评审真正分离。

## 角色

| 角色 | 可以做 | 不可以做 |
|---|---|---|
| 项目 AI | 制作、自检、修改、提交证据 | 决定自己最终通过 |
| 裁判 AI | 盲评、评分、发修订单 | 修改项目或降低标准 |
| 验证工具 | 运行测试、构建、文件和数字检查 | 判断主观偏好 |
| 用户 | 接受、附条件接受或拒绝 | 把事实错误写成技术合格 |
| 系统 | 冻结规则、计算裁定、保存记录 | 静默改变模式或阈值 |

## 制作阶段

项目 AI 可以像 Quick Check 一样进行内部制作循环：

1. 读取合同。
2. 制作成果。
3. 自检明显问题。
4. 在提交前自行修复。
5. 冻结当前版本并提交。

内部自检只用于提高提交质量，不是最终评审。

## 自动调度

Skill 负责自动启动隔离评审，不要求用户手动另开聊天。

可使用宿主提供的子任务、Agent 或独立会话机制。裁判上下文必须：

- 不继承制作对话历史。
- 只读取冻结评审包。
- 不读取制作者的预期分数和解释。
- 只能返回评审结果，不能修改成果。

裁判启动失败时重试一次。仍失败时，自动生成带 `fallback_reason` 的 Quick 回退运行，并继续走完项目、自检和报告流程。报告必须标记 `strict_satisfied: false`。

裁判必须执行任务，而不是只确认任务。父运行应等待裁判结束，并检查约定的 `review.json`。空回复或只有确认文字时，记录 `acknowledgement_only` 并重试。

## 评审包

裁判只能拿到：

- 原始需求。
- 冻结后的合同。
- 当前版本成果。
- 结构化证据。
- 启动和使用说明。
- 评分规则。

裁判不能拿到：

- 制作者完整对话。
- 制作者预期分数。
- 制作者对评审问题的预先辩护。
- 其他裁判的最终分数。

## 评审顺序

1. 运行确定性检查。
2. 裁判按合同逐项给出需求状态。
3. 检查证据覆盖和 P0。
4. 记录问题与建议修复目标。
5. 用户进行最终判断。
6. 系统合并结果并输出裁定。

裁判返回的结构化评审只是中间材料。必须写入运行的 `review` 字段，完成用户终审，并通过门禁生成 `verdict.md` 后才算结束。

## 终止检查

Strict 不能在独立裁判结束后直接停止。结束前必须确认：

- 评审版本与冻结提交版本一致。
- P0 和证据覆盖已计算。
- 用户已经接受、有条件接受或拒绝。
- 门禁脚本已运行。
- `verdict.md` 已生成。

缺少用户决定时，状态只能是 `awaiting_user_decision`，不能阻塞报告生成。

## 修订单

裁判不直接修项目，只输出可复评的修订单。每项至少包含：

- 问题编号。
- 对应需求。
- 优先级。
- 可观察的问题。
- 必须完成的修改。
- 复评测试。
- 修改范围限制。
- 当前轮次。

## 复评

下一轮至少检查：

- 本轮修订单是否完成。
- 新增证据是否有效。
- 已通过的 P0 是否发生回归。
- 是否发生范围外修改。

用户与裁判冲突时：

- 客观问题由证据裁决。
- 主观价值由用户裁决。
- 无法裁决时继续修订或标记争议。
